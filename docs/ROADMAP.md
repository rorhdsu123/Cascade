# Cascade — 출시 로드맵

> 출시 계획 자립 문서. **상세 결정·근거는 `SPEC.md` §8 + 결정 로그 C50이 정본**이고, 이 문서는 그 요약·실행판이다.
> 확정일 2026-07-18 (C50). 팀: **기획·개발 = 유저 + Claude / 아트 = 별도 디자이너(병렬)**.

---

## 1. 출시 전략 (한눈에)

**라이브서비스 듀얼코어 + 데이터-먼저 소프트런치.**

- **듀얼코어**: 캠페인(스테이지)과 무한 모드가 **둘 다 코어**. 어느 하나가 부차가 아니다.
  - **캠페인** = 숙련·진행·authored 챌린지 → *"다음이 보고 싶다."*
  - **무한** = 표현·경쟁·하이스코어 → *"내 최고를 깬다."*
  - **교차 공급**(서로 잠식 안 하게): 공유 소프트 재화 · 코스메틱 양쪽 적용 · 하드 로스터(장갑·점착·분열)는 후반 캠페인 + 랭크 무한 양쪽 등장.
- **데이터-먼저 소프트런치**: 두 기둥을 얇게-좋게 내고, **어느 쪽을 플레이어가 사랑하는지 실측** → 라이브옵스 예산을 그쪽에 집중. 콘텐츠 예산을 미리 못박지 않는 게 소프트런치의 존재 이유.
- **셸 = 리더보드-먼저**: 소프트런치 셸은 무한 점수 **리더보드**(경쟁 천장). Play Games / Game Center = 백엔드 0, 아트 트레드밀 0. 코스메틱 셸은 IAP 층으로 후속.

> 왜 무한이 리텐션을 떠받치나: 무한은 정의상 "무한 일수 콘텐츠"라 7일+ 리텐션을 자동으로 먹는다. 스테이지는 유한하므로 **깔때기 겸 1주차 기둥**이지 7일을 채우는 물량이 아니다.

## 2. 수익 모델 (광고 우선 → IAP 나중)

소프트런치 = 광고 위주. IAP(코스메틱)는 데이터 보고 후속.

| 광고 포맷 | 설명 | Cascade 적합성 |
|---|---|---|
| **리워드 광고** | 자발 시청 → 보상 | ★ 코어. 부활(C48)이 이미 이 형태. 비강제라 코지 톤 유지 |
| **인터스티셜** | 자연 브레이크에 전면 광고 | ○ 스테이지 전환·판 종료. **빈도 캡 필수**(과하면 코지 파괴) |
| 리워드 인터스티셜 | 스킵 가능 + 보면 보상, 인트로로 opt-out | △ 인터스티셜의 온건판, 테스트 후보 |
| 배너 | 상시 띠 광고 | ✗ 코지 훼손 + 세로 보드 가림. 회피 |
| 앱 오픈 광고 | 앱 실행/복귀 시 | ✗ 첫인상 저해·공격적. 회피 |
| 네이티브 | UI에 녹인 광고 | △ 홈/상점 메뉴에 한해 후속 검토 |
| 오퍼월 / 플레이어블 | 오퍼 완료 보상 / 인터랙티브 | — 오퍼월은 코지 부적합, 플레이어블은 주로 UA(유저확보) 도구 |

- **소프트런치 확정 = 리워드(부활) + 인터스티셜(빈도 캡).**
- 배너·앱오픈은 코지 코어와 세로 화면을 해쳐 **제외**.
- 추가 포맷은 실데이터 + 현행 AdMob 정책 조사 후 도입.
- **IAP = 코스메틱**(광고 제거·스킨). 소프트런치 미포함, 데이터 보고.

## 3. 개발 로드맵

> 기간은 **코어가 이미 완성된 전제**의 추정치. 아트 트랙은 개발과 동시 진행.

### 개발 트랙 (유저 + Claude) — 순차

| Phase | 내용 | 대략 | 산출물 |
|---|---|---|---|
| **0. 모드 아키텍처** | `modes/game_mode.gd` director를 `Main.gd`에 통합 · `StageMode`(현 STAGES 래핑) + `EndlessMode` · `modes/` 커밋 | **~3~5일** | 코어가 모드-무관, 무한모드 형제로 꽂을 이음새 |
| **1. 무한 코어 + 리더보드** | EndlessMode(승리 없이 램프, 레버 = 전진 속도) · 점수 = 생존 깊이 · 로컬 베스트 → 플랫폼 리더보드 | **~1.5주** | 경쟁 코어 + 얇은 셸 |
| **2. 모바일 배관** | 터치 입력(드래그 C32 → `InputEventScreenDrag`) · 세로 실기기 사이징 · 세이브/영속 · KR 폰트(C22③) · **광고 SDK**(리워드 + 인터스티셜, AdMob + 미디에이션) | **~2주** | 실기기에서 돌고 돈이 되는 빌드 |
| **3. 캠페인 확장 + 소프트런치 셸** | 스테이지 5 → **12~15**(데이터 + `sim.gd` 곡선 검증) · 홈 / 리더보드 UI / 설정 / 통계 | **~1~1.5주** | 두 기둥 + 셸 완비 |
| **4. 런치 옵스** | 애널리틱스(D1/D7·광고 fill·부활율) · 스토어 에셋 · 빌드 파이프라인(안드로이드 먼저) · 1지역 소프트런치 | **~1~1.5주** | 스토어에 오른 소프트런치 |

**→ 소프트런치까지 대략 6~8주.**

## 3-B. kill / promote 게이트 (Phase V ⑫)

> 확정 2026-08-12. **소프트런치를 시작하기 전에 박아 둔다** — 끝나고 정하면 "느낌상 괜찮은데?"로 흘러서
> 소프트런치가 그냥 조용한 출시가 된다. 숫자는 2026년 퍼즐 장르 실측 벤치마크를 기준선으로 삼되
> **게이트는 그보다 보수적으로** 뒀다. 우리가 묻는 건 "상위권인가"가 아니라 "될 물건인가"다.

| 축 | 지표 | 확장 | 재설계 | 중단 | 기준선 |
|---|---|---|---|---|---|
| **붙잡나** | D1 리텐션 | ≥ 35% | 25–35% | < 25% | 퍼즐 장르 중앙값 31.9% · "좋음" 프로파일 35% |
| **남나** | D7 리텐션 | ≥ 12% | 6–12% | < 6% | 퍼즐 장르 중앙값 12.2% · 전 장르 8–14% |
| **깊나** | 세션당 클리어 판수 | ≥ 3판 | 2–3판 | < 2판 | 우리 북극성. **현재 봇 실측 1.0판** |
| **도나** | 부활 시청률(제안 대비) | ≥ 40% | 15–40% | < 15% | 캐주얼 퍼즐 리워드 opt-in 64% — 죽음 순간이라 보수적으로 |
| **버나** | D7 LTV ÷ CPI | ≥ 1.0 | 0.5–1.0 | < 0.5 | Tier-1 리워드 eCPM $15–40 |

**ARPDAU는 새 배선 없이 만든다** = AdMob 콘솔 수익 ÷ 우리 계측 DAU. impression-level revenue API를
플러그인에서 뚫을 필요가 없다(네이티브 작업 0).

⚠**게이트를 클로즈드 테스트(테스터 12명)에 적용하지 않는다.** 12명으론 D1조차 못 읽는다 — 한 명이
앱을 안 열면 8%가 흔들린다. 클로즈드는 **결함 발견**용이고, 위 숫자는 UA 코호트에서만 판정에 쓴다.
D7을 신뢰하려면 최소 200~300 설치가 필요하고, **안 차면 판정을 미루지 예산을 늘리지 않는다.**

⚠**"깊나" 축은 지금 우리 중단선 아래다**(봇 1.0판 < 2판). 게이트를 낮추지 않고 **처방 슬롯을 비워 두는**
쪽을 택했다 — 클리어 직후 무엇이 두 번째 판을 막는지 퍼널로 진단하고 고친다. 목표 전환율은 이 축에서
역산한다: 클리어 후 이어질 확률을 `p`라 하면 세션당 클리어는 대략 `1/(1−p)`이므로 **3판 ≈ 67%, 2판 = 50%**다.
진단·처방을 다 쓰고도 못 넘으면 **그때 2판으로 낮추는 게 정직한 대응**이지 밀어붙이는 게 아니다(낮춘 기록을 남긴다).

⚠**"버나" 축은 구조적으로 불리하게 시작한다.** 부활은 판당 1회 캡이고 인터스티셜은 노출 off라
views/DAU가 낮게 고정된다(벤치마크 2.1 views/DAU, 우리는 죽어야 1회). 알고 건 상한이다 —
`AD_PLAN.md` §1이 이미 "광고 수익 상한을 스스로 거는 선택"이라 적어 뒀다. **이 축이 재설계 구간에
떨어지면 게임을 고치기 전에 캡부터 푼다**(값 하나로 2~3회가 된다).

## 3-C. 웹 루프 통과선 (루프 1·2·3)

> 확정 2026-08-13. **§3-B를 웹 플레이테스트에 그대로 들이대면 안 된다** — 저건 UA로 사 온
> 모바일 설치 코호트의 자다. 웹 루프는 설치가 없고 사람을 모집해서 부른다. 그런데 통과선이
> 아예 없으면 데이터를 받아도 판독이 아니라 **인상**이 된다(루프 2의 전환율 67%만 있었다).
> 여기 숫자는 루프를 돌리는 동안 **무엇을 고칠지 정하는 자**이고, 출시 판정은 §3-B가 한다.

| 루프 | 묻는 것 | 지표 (단위) | 확장 | 재설계 | 중단 |
|---|---|---|---|---|---|
| **1** | 첫인상 | 첫 판을 시작한 **방문** 비율 | ≥ 90% | 75–90% | < 75% |
| **1** | 붙잡나 | 60초를 넘긴 **방문** 비율 | ≥ 75% | 50–75% | < 50% |
| **2** | 깊나 | 두 번째 판까지 간 **방문** 비율 | ≥ 67% | 50–67% | < 50% |
| **3** | 남나 | 다음 날 이후 돌아온 **사람** 비율 (웹 D1) | ≥ 20% | 10–20% | < 10% |

판독은 `python3 tools/funnel.py 이벤트.csv`. 위 네 줄이 그 도구가 내는 퍼널의 네 칸이다.

🔴**단위는 '세션'이 아니라 '방문'이다(2026-08-14 정정).** 처음엔 세션으로 박았는데, 폰은
화면 잠금·알림·앱 전환마다 세션이 끊긴다 — 첫 코호트에서 세션 33건 중 12건이 4초 미만이었고
한 사람이 하루에 11개를 만들었다. 그 파편을 분모에 넣으면 같은 자료가 **첫 판 시작 34% vs 83%**로
갈린다. 사람 행동을 나타내는 건 뒤쪽이다. 게임 쪽은 C198에서 5분 유예를 넣었고, 그 전 데이터는
`funnel.py`가 같은 기준으로 되붙인다. **두 값이 어긋나면 방문 쪽이 맞다.**

**루프 1 — 왜 90%와 75%인가.** 둘 다 게임 안의 실측 시간에서 나온다. 판 하나는 **71~102초**이고
(승배치 기준, S19) 첫 줄은 **10~15초**에 지워진다(봇 실측, S24). 그래서 60초는 *한 판을 끝내기엔
모자라지만 첫 쾌감은 이미 네 번쯤 지났을* 시간이다 — 여기서 나갔다면 첫 줄을 지우고도 안 붙잡혔거나
아예 시작을 안 한 것이다. 그 둘은 처방이 완전히 다르므로 **'첫 판 시작'을 앞 칸으로 따로 뽑는다.**
켜고 시작조차 안 하는 비율이 10%를 넘으면 그건 게임이 아니라 첫 화면 문제다.

**루프 2 — 67%는 §3-B에서 이미 역산된 값이다.** 클리어 후 이어질 확률을 `p`라 하면 세션당 클리어는
대략 `1/(1−p)` → **3판 ≈ 67%, 2판 = 50%**. 즉 이 줄은 새 기준이 아니라 "깊나" 축을 세션 단위로
번역한 것이다.

**루프 3 — 이 숫자는 모바일 D1과 직접 비교하지 말 것.** 두 힘이 **반대 방향으로** 작용해서 배율을
정직하게 낼 수가 없다: ①웹엔 홈 화면 아이콘이 없다 = 모바일 D1의 상당 부분을 만드는 '아이콘을 보고
누르는' 경로가 통째로 없다(내림) ②모집해서 부른 사람이라 의무감이 붙는다(올림). 그래서 루프 3의
1차 판정은 **절대값이 아니라 "0이냐 아니냐"**이고, 2차가 **루프 간 방향**이다 — 같은 모집 방식으로
같은 자를 대므로 처방 효과는 차이로 드러난다. 위 20/10은 그 위에 얹은 보수적 바닥일 뿐이다.

⚠**표본이 통과선보다 먼저다.** 15~20명으로는 D1을 비율로 읽을 수 없다 — 한 명이 5~7%p를 흔든다.
루프 3의 누적 50명 목표가 그래서 있고, **50명 아래에서는 비율 대신 '복귀자 수'만 읽는다.**
`funnel.py`가 n<30이면 경고를 같이 찍는다.

⚠**웹 통과선은 §3-B로 승격되지 않는다.** 루프는 11월에 낼 게임을 고치는 도구지 판정 기구가 아니다.
확장/재설계/중단 판정은 UA 코호트에서 §3-B로만 한다.

⚠**못 넘으면 낮추되 기록을 남긴다** — §3-B와 같은 규약이다. 진단·처방을 다 쓰고도 못 넘을 때
정직하게 낮추는 것과, 데이터를 보고 나서 기준을 옮기는 것은 다르다. 낮춘 날짜와 이유를 여기 적는다.
