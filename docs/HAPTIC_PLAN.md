# 햅틱 설계 (R1) — BlockCastle

정본 문서. 코드의 접점은 `Main.gd`의 `===== 햅틱 =====` 블록 한 곳이고, 감사는 `tools/haptic_probe.gd`가 한다.

## 1. 왜 지금, 왜 값싼가

- **소리가 통째로 없다.** `sound_on`·`bgm_on`은 오디오 시스템 없이 '예약된 선호'로만 저장돼 있다. 즉 이 게임은 지금 **시각 단일 채널**이고, 모바일은 대부분 무음 플레이라 햅틱은 두 번째 채널이 아니라 **무음 플레이어에게 유일한 비시각 피드백**이 된다.
  - ⚠**갱신(2026-08-03)**: 이 전제는 작성 시점(7/30)의 사실이고 **지금은 오디오가 붙어 있다**(`AUDIO_PLAN.md`, main 병합 완료). `bgm_on` 토글은 제거됐다(C127 — BGM을 안 만들기로 확정). **논지는 그대로 산다** — 모바일 무음 플레이 비중 때문에 햅틱이 유일한 비시각 채널이 되는 상황은 여전하고, 이제는 오디오와 **같은 이음새를 공유**한다.
- **비용이 0에 가깝다.** 에셋 없음, 번들 증가 없음, 파이프라인 없음. `VIBRATE` 권한은 이미 켜져 있다(`export_presets.cfg`, RELEASE.md의 권한 정본 = INTERNET+VIBRATE) → 매니페스트·심사 표면 변화 없음.
- **단일 임팩트 채널 패턴이 이미 있다.** `shake_timer = maxf(shake_timer, SHAKE_DUR * k)` — 호출부가 세기를 등급화하고 승자독식으로 합친다. 햅틱은 그 형제로 붙었고, 호출부도 대체로 같은 자리다.

동결(ROADMAP §5, 2026-07-27)과의 관계: 형식상 '도파민 연출'이라 동결 대상이지만, **W1의 사람 플테를 무음+무촉각 빌드로 재면 코어를 과소평가한 답이 나온다**는 근거로 '플테 전 검증 보조'로 진행(유저 판단, 2026-07-30).

## 2. 원칙 다섯

1. **희소 채널이다 — 시각의 메아리가 아니다.** 시각 이벤트마다 진동을 얹으면 캐스케이드 한 번에 십수 발이 나가고, 안드로이드는 새 호출이 진행 중인 걸 취소·대체하므로 결과는 리듬이 아니라 **고장 난 폰 같은 뭉갬**이다.
2. **액추에이터가 하나 = 믹서 필수.** 불응기(같거나 낮은 우선순위는 드롭, 높은 것만 선점) + 롤링 예산(초당 진동시간 상한).
3. **캐스케이드는 반복이 아니라 하나의 형태로.** 링이 순차로 터져도 진동은 다운비트 한 발. 연쇄의 맛은 시각 순차 재생이 담당한다.
4. **구분은 세기가 아니라 종류로.** 목표는 강한 진동이 아니라 **눈 감고도 구분되는 것**.
5. **의미는 길이·박자에 싣는다.** amp는 하드웨어 의존이라 진폭 제어가 없는 폰은 전부 최대 세기로 낸다. Godot이 `hasAmplitudeControl()`을 안 열어주니 분기도 불가 → 세기만 다른 어휘는 만들지 않는다.

## 3. 어휘 — 셋뿐

| 단어 | 물리 | 언제 | 우선순위 · 불응기 |
|---|---|---|---|
| **tick** | 12ms, amp 0.30 | 조각 착지 | 0 · 0.09s |
| **pop** | 30→45ms, amp 0.55→1.00 (콤보 1→8), 콤보≥4는 +0.09s 둘째 박 | 줄 삭제 다운비트(섬광과 같은 프레임) | 1 · 0.16s |
| **roll** | 18·18·90ms 3박(짧-짧-김) | 스테이지 클리어 · 무한 PB 돌파 — **판당 1회** | 2 · 0.40s |

박자 수·길이만으로 1짧 / 1중 / 3박으로 갈리므로 amp 없는 기기에서도 구분이 살아남는다.

숫자 근거 = 안드로이드 공식 햅틱 원칙: 좋은 키클릭 **10~20ms**, 잦은 이벤트일수록 **약하게**(빈도↔세기 반비례), *"less is more — 과하면 유저가 OS에서 아예 끈다"*.

**손실에는 아무것도 없다.** 누수·거점사·막힘사 전부 무햅틱 = *"축하만 몸으로, 손실은 눈으로"*. 코지 코어 톤과 싸우지 않게 하려는 결정이고, 없다가 넣는 게 넣었다 빼는 것보다 판단이 쉽다(유저 결정, 2026-07-30). 손실 텍스처(`thud`, 100~140ms 1발)는 기기 실측 후 재고 대상.

**기각(나중에 "왜 없지" 하지 않도록):** 적 전진(매 턴 = 뭉갬) · 개별 처치(캐스케이드 뭉갬) · UI 버튼 탭(안드로이드 시스템 터치 피드백과 이중 진동) · 드래그/호버 · **배치 실패 버즈**(탐색을 벌하는 건 '안전하게 배우는 재미'와 정면 충돌 — 레퍼런스도 여기 아무것도 안 한다).

## 4. 이음새

- **접점 한 곳**: `Main.gd`의 `_haptic(kind, intensity)` → `_hap_fire()` → `Input.vibrate_handheld()`. 호출부는 '무엇이 일어났나'만 말하고 세기·드롭·박자는 전부 믹서가 정한다. `_hap_step(delta)`는 `_process` 맨 앞(메뉴·히트스톱 조기 반환보다 먼저 — 예약 박이 끊기면 모티프가 반 토막 난다).
- **호출부 4곳**: `_place_piece`(tick) · `_burst_lines`의 `flash_timer = FLASH_DUR` 직후(pop) · `_check_win`(roll) · `_process`의 PB 돌파 분기(roll). 설정 토글을 켤 때 확인용 `pop` 1발(기기에서 어휘를 재생해 보는 유일한 트리거).
- **관찰만**: 게임 값도 RNG도 안 건드린다 → `tools/regress.gd` 골든 불변. `_hap_t`는 벽시계가 아니라 delta 누적이라 프로브가 결정적으로 재현된다.
- **설정**: 기어 모달 세 번째 토글(기본 on), `user://settings.save` 3번째 바이트. **길이별 단계 읽기 필수** — user://는 트렁크·워크트리·구버전 빌드가 같이 쓰므로 구버전이 쓴 2바이트를 새 코드가 읽어도, 새 코드가 쓴 3바이트를 구버전이 읽어도 안전해야 한다. 토글이 셋으로 늘어 행 간격을 70→58px로 좁혔다(패널 높이 불변 = 긴 화면에서 아래로 안 삐져나감).
- **플랫폼 게이트**: `_hap_ok = OS.has_feature("mobile")` — 데스크톱·에디터는 no-op(로그만).

## 5. 엔진 사실 (직접 확인)

- `Input.vibrate_handheld(duration_ms: int = 500, amplitude: float = -1.0)` — 4.6.2 doctool 확인. amp는 `CLAMP(int(amp * 255), 1, 255)`로 변환, `-1`은 DEFAULT_AMPLITUDE.
- **안드로이드**: `GodotNativeBridge.kt`가 `VibrationEffect.createOneShot(ms, amp)` 호출(API 26 미만은 `vibrate(ms)`). ⚠**이건 안드로이드 지침이 "buzzy하니 피하라"고 한 그 레거시 원샷 경로다** — 크리스프한 딸깍(컴포지션 프리미티브 TICK/CLICK)은 기본 API로 못 낸다.
- **탈출구(R2)**: Godot 자체 계측 에셋이 순수 GDScript로 `Engine.get_singleton("AndroidRuntime")` → `getSystemService("vibrator")` → `JavaClassWrapper.wrap("android.os.VibrationEffect")` 패턴을 쓴다 = **네이티브 플러그인 없이** 프리미티브·`hasVibrator()`에 도달 가능. 기기에서 buzzy 판정이 나면 `_hap_fire` 몸통만 갈아끼운다.
- **iOS**: `supports_haptic_engine()`이면 Core Haptics(iOS 13+)로 지속·세기 둘 다 전달 → 어휘가 그대로 살아남는다.
- **웹**: `navigator.vibrate(duration)` — amp 버려짐. **데스크톱**: no-op.

## 6. 레퍼런스(Block Blast) 조사 결과 — 원격으로는 검증 불가

- 진짜 Block Blast!(Hungry Studio / ARETIS LIMITED, App Store id1617391485)의 설명·기능·업데이트 내역 전체에 haptic·vibration 언급이 **0회**.
- 검색 결과가 **동명 클론으로 오염**돼 있다. `Stack Block Blast` 등 별개 앱의 스토어 카피에 *"Feel every explosion through haptic feedback"*, *"Vibrate on Perfect Stack"* 같은 문구가 있어, 요약만 믿으면 **클론 카피를 레퍼런스 사양으로 착각**한다.
- "진동 끄는 법" 콘텐츠는 많지만 실내용은 전부 OS 설정 안내 → 게임 내 토글의 존재 여부도 미확인.
- 근본적으로 **햅틱은 프레임에 안 남아 재검증이 불가능**하다. 원본 프레임으로 되돌아갈 수 있는 시각 레퍼런스와 다르고, 유일한 지상 검증은 **기기 위의 엄지**다.

**실측 프로토콜(기기 붙일 때 20분)**: 폰을 딱딱한 책상에 놓고 OS 햅틱 on·게임 사운드 off로 두고, **다른 기기로 모터 소리를 녹음**한다(책상 공진 덕에 파형에서 지속·박자를 ±5ms로 읽을 수 있다). 장면 셋만: ①착지 10회 ②1줄 삭제 ③3줄+ 콤보. 답이 필요한 질문 넷: **매 착지에 있나 / 삭제가 착지보다 긴가 / 콤보가 여러 발이냐 한 발이냐 / 실패에 뭐가 있나.** 덤으로 게임 내 진동 토글 유무 눈으로 확인.

## 7. 검증 상태

`tools/haptic_probe.gd` (시드 20250123 고정, 창 모드) — **11검사 PASS**:

| 실측 | 값 |
|---|---|
| 사람 템포(1.8s/수) | 19발 / 27.9초 = **초당 0.68발**, 롤링 1초 최대 **2발·44ms** |
| 스트레스(최고속) | 초당 2.32발, 롤링 1초 최대 **3발·74ms**, tick 드롭 8건(불응기 작동) |
| 어휘 | pop 2박 간격 0.100s · roll `18·18·90` ×2판 · 같은 판 두 번째 roll = `once` 드롭 |
| 결정성 | 같은 시드 두 패스 로그 완전 동일(햅틱 경로 RNG 미사용) |

`tools/regress.gd` (PROBE_SEED=20260718 N=20) — **골든 byte-identical**.

⚠**기기 미검증.** 세기가 적당한가 · tick이 거슬리는가 · buzzy한가는 실기기에서만 답이 나온다. APK는 트렁크에 병합한 뒤 트렁크에서 빌드한다(`android/`가 .gitignore라 워크트리엔 빌드 템플릿이 없다).

프로브 함정 두 개(실측으로 드러남): ① 봇은 프레임 없이 연달아 놓으므로 **사람 템포를 명시적으로 흘려보내야** '초당 발화수'가 의미를 갖는다 ② 봇은 14수 예산 안에 스테이지를 못 깨고 콤보 4도 못 만들어서, 패스 A·B만으론 roll·2박이 **한 번도 실행되지 않고 검사가 공허하게 초록**이 된다 → 어휘를 직접 때리는 패스 D가 필요하다.

## 8. 남은 것

1. **기기 실측** — 위 프로토콜 + 세기 튜닝. 1번 항목은 '매 착지 tick이 거슬리는가'.
2. **R2 판정** — buzzy하면 `_hap_fire`를 JavaClassWrapper 프리미티브로 교체(안드로이드 전용, 실패 시 현 경로로 폴백).
3. **`thud` 재고** — 손실 햅틱을 넣을지는 기기에서 톤을 느껴본 뒤.
4. **선택**: 애널리틱스에 `haptic_on` 1필드(유저가 끄는 비율) — 새 이벤트가 아니라 `run_started`의 필드로.
